## [0.6.0] — 2026-08-15

The **exit** half of the SDLC. Every gate apex had guarded an *entry* condition — may this work start, is it declared, is it reviewed, is it releasable — and none guarded the mechanical moment a release is declared **done**. Measured on a real repo over its first 33 days: **47 milestones open, 0 closed, 11 of them holding zero open issues**, three of those releases of the very component its operator believed was incomplete. Nothing was broken; every issue had closed correctly through `Closes #N`. There was simply no moment anywhere saying "this release is done, stop touching it", so the tracker could not display success and the project felt permanently incomplete. **A process that cannot say *done* converts finished work into felt failure.**

### Added

- **`apex:release-loop` — the milestone-demo release loop, apex's first EXIT gate.** A release is a **milestone whose done is a numbered, operator-runnable demo**; issues map **1:1 to demo steps**, each with a **falsifiable** `Done when` (an observation that could come out the other way — "the golden test compares both lanes and asserts the rows match" can fail, "a decision is recorded" cannot, and unfalsifiable acceptance is how design work gets counted as delivery); the first PR is the demo's **walking skeleton, failing honestly, walls before rooms** (frozen wire DTOs / seam contracts / typed Protocols, each landing with the test that pins it — a wall no test pins is a drawing); the milestone closes when the operator runs the demo. For a `vn`, the spec is a **dated amendment to the living design, never a second dossier** — measured, per-version snapshots die unread and living documents survive. Sits **around** `apex-flow` (which governs plan→design→implement *within* a slice) and hands to `release-readiness` at SHIP; bugs route to `investigate-bug` plus the defect form. Five refusals, including a milestone whose description holds no demo, and reopening a closed release to append work (that is the next version).
- **`templates/gates/milestone_completion_gate.py` — the gate that closes the loop, on a *scheduled* lane.** Reports milestones that are open, hold no open issues, hold at least one closed issue, and finished longer ago than a **24h grace period**. Four design decisions, each against a specific failure: **the clock is `max(closed_at)` across the milestone's issues, never the milestone's `updated_at`** — `updated_at` moves when a description is edited or an issue retitled, so one edited word would reset a six-week-old release's age to zero and the gate would never fire on the milestones abandoned longest; **REST, never the search API** — search is unavailable in some repos and answers an unavailable search with an *empty list* rather than an error, which reads as "no findings" and takes the gate permanently and silently green; **empty milestones are skipped** — a release nobody started is not a release nobody closed, and reporting them buries 11 real findings under 36 placeholders; and **the grace period is load-bearing** — at zero it fires between a release's final merge and the operator closing the tab, and a gate that fires on correct work teaches people to reach for `--admin`, which skips every *other* check too. All issues closed but no `closed_at` **raises**: that is a read that did not work, and guessing either way turns a broken credential into a silent pass or a wave of false findings. Structured as a pure function with the timestamp lookup **injected**, so the whole decision table is driven with no token and no network. Scheduled rather than PR-lane because the condition becomes true *after* the last PR merges, when no PR lane is running.
- **`templates/gates/acceptance_check.py` — a PR that closes an issue must answer that issue's `Done when`.** Extracts **only the bullets under the acceptance heading, stopping at the next heading** — a GitHub issue form renders each field as its own heading and the work-item form puts a `Production caller` path list directly after `Done when`, so running to the end of the body makes the check demand the PR tick off file paths. **Prose acceptance yields no criteria and is NOT a finding** (plenty of real issues state acceptance as a paragraph; failing those fires the gate on correct work). Comparison is **normalised** — an author who drops the bold while ticking is doing nothing wrong. An unreadable issue **raises** rather than reporting "no criteria". Ships `--print-checklist` emitting the pasteable block, whose bullet text is the criterion **verbatim** so that pasting it and ticking actually clears the check — a check is only fair if satisfying it is trivial. **Stated limits, in the docstring:** it cannot tell whether a ticked box is true, and it cannot make an unfalsifiable criterion good. It buys a forced re-read of the issue at close time; that is all it buys.
- **`hooks/acceptance_checklist.py` (PreToolUse, Bash) — the advisory half.** On `gh pr create` / `gh pr edit` whose body closes issues, injects the unanswered criteria as a pasteable tick-box block. **Advisory on purpose** — the blocking version runs in CI where an author can fix and push; a denial here would fire on a body one paste away from correct. Silent when there is nothing to inject (all ticked, or prose acceptance): it runs in front of a command somebody is waiting on, and confirming that a correct body is correct is how an advisory hook gets ignored. **A failed issue read is stated, never swallowed** — "this issue has no criteria" and "the token could not read this issue" produce identical silence, and the first is what the reader assumes. Imports the gate rather than reimplementing its extraction rules, so the advisory message and the blocking check cannot drift.
- **`hooks/issue_cap.py` (PreToolUse, Bash) — the rate, not the judgement.** Silent on a session's first `gh issue create`; from the second on, reports the count, the measurement (**78% of that repo's open backlog was agent-filed, largest lane being issues about triaging issues**) and the alternative (put it in the PR body). Every one of those issues was a real observation filed by an actor for whom filing costs nothing, which is exactly why the *rate* is the finding and no single issue is. The counter lives in a **temp directory, never the repo** — a hook that dirties the working tree makes every `git status` lie and gets its bookkeeping committed into somebody's PR.
- **`hooks/session_output_gate.py` (PreToolUse, Write) — session narrative goes in the PR body.** Flags a **new** `.md` under `docs/` whose basename names the write-once genre (handoff, sweep, readiness, triage, autonomous-session, completion-log, dated log/inventory/freeze/audit) and points it at the PR body, where it reaches the same reader attached to the change that produced it. Measured: **of 568 documents, 16 stayed maintained — all living registries — and 383 were written once and never revisited.** The exemption list is pinned by name (`GAPS.md`, `DECISION_LOG.md`, a standing `HANDOFF.md`, at the top of `docs/` where a standing register lives) plus exempt directories (`lessons/`, `templates/`, `adr/`), because **a hook that nags the 3% that work in order to stop the 67% that do not has it backwards**. Advises on **Write only, never Edit** — nagging every touch of a legacy file teaches sessions to skim past the hook.
- **`templates/milestone.md` — the milestone *description* shape** (not a repo file). Title is an outcome a person can watch; first line links the dossier; then `DONE = THIS DEMO, run by the operator` with numbered observable steps mapping 1:1 to issues, the **real input named** (a demo on a fixture demonstrates the fixture), and the **scope valve written in advance** — written before the work starts it is a rule; written when the tempting issue appears it is a decision made under pressure by the person who wants to say yes.

### Changed

- **`templates/github/work-item.yml` — `Done when` now demands falsifiability and names the counter-example.** An observation that could come out the other way, with "a decision is recorded" called out as the thing that cannot fail, and "tests pass" named as the same defect wearing a test's clothes. Also states that the issue should be exactly one numbered step of its milestone's demo.
- **`templates/github/defect.yml` gains two required fields.** **Consecutive runs** — for anything nondeterministic, the ratio over **N ≥ 5 consecutive runs in isolation**, because a nondeterministic failure hands out one lucky green for free and a single passing re-run cannot be told apart from a fix (the form-level counterpart of `test-strategy` rule 18). **Regression guard** — the test that would have caught this, named as a test, landing in the fix PR and failing on the unpatched tree; "no test could have caught it" is an honest answer that feeds the existing gate question.
- **`hooks/_hooklib.py` gains the shared `gh`-command plumbing** — `invocation_index`, `flag_values`, `submitted_body`, `plugin_root` — moved out of `artifact_templates.py` rather than forked into the new hook. Each carries a measured reason in its docstring (the substring match that fired on a `git commit` mentioning `gh issue create`; the unreadable `--body-file` that produced a confident "you are missing all 7 sections"), and a second copy is how those reasons get lost.
- **`hooks/_hooklib.py` gains `command_key`, fixing a silent bug in `artifact_templates.py`.** The once-per-command muting was keyed on `hash(command)`, and **Python salts string hashing per process while every hook invocation is a new process** — so the key differed on every call, the marker was never found again, and the muting had never worked. It looked fine because the symptom is a hook that speaks, which is also what a hook with something new to say looks like. Now a stable SHA-256 prefix, used by both hooks.
- **`.github/workflows/hook-tests.yml` runs `templates/gates/tests/` too.** `templates/**` was already in the workflow's paths filter; only the suite was missing, so the existing gate tests were present and never ran in CI.
- **`apex:install-gates` carries both new gates**, with the acceptance step added to the PR job and the completion gate documented as its own **scheduled** lane — including the explicit instruction *not* to add it to branch protection, since it is a report about the tracker rather than a verdict on any PR.

### Testing

Each gate ships with **planted defects and its false-positive rate measured before its true positives**, because green on a first run is the least informative signal available — an implementation that returns `[]` is also green. **25 mutations were applied for real** (one guard removed at a time, suite run, guard restored) and all 25 turn the suite red. Four survived the first pass and were genuine holes in the tests rather than in the code: a no-criteria case whose bullets sat where the extractor stopped anyway, a counter-location test that used the env override and so never exercised the default path, a `docs/`-scope test whose filename was also name-exempt, and a substring-match test whose body flag sat inside the quoted commit message. Each is now fixed with the reason recorded in the test's own docstring. Every list-shaped allow/denylist gets a case from **outside** its own list — including one that documents an honest limit rather than a bug (`2026-08-15-postmortem.md` is the same genre and is not flagged, because a name-shaped rule reads names).

## [0.5.0] — 2026-08-13

Seven learnings from one engineering postmortem, folded into the gates that should have caught them. Five strengthened an existing rule with the measurement it lacked; one is new; one was split — the half apex owns was folded in, the half `superpowers:systematic-debugging` owns was left there.

Plus a hook audit, measured rather than reasoned: **nine hook processes fire on every edit and three on every message; two of the nine are apex's own fork of a hook the host repo already registers, and one of the three was wrong all three times it was observed firing.** Four behaviour repairs and one new hook, and the rule the whole audit reduces to — *a hook that fires wrongly does not merely waste a process, it teaches you to ignore hooks generally, which is how the correct ones stop working.* Nothing here removes a gate: the one hook whose matching was measured wrong keeps every gate it enforced and loses only the guessing.

### Added

- **`hooks/session-baseline.sh` (SessionStart) — a snapshot of what was already dirty, so the Stop nudge can subtract it.** One line per already-changed path, `<blob-sha><TAB><path>`, written atomically into the same marker directory `suggest-review-on-stop.sh` already uses. **Content hashes, not a status list:** a file that was already modified and is modified *again* by this session keeps its `M` status, so only the hash moves. Deletions are recorded as `-` so a path somebody else removed is not read back as this session's work. The **first** SessionStart of a session wins — `clear` and `compact` re-fire the event with the same `session_id`, and re-snapshotting there would silently reclassify everything written before the compaction as another session's. Emits nothing (SessionStart output becomes session context, and this hook has nothing to tell the agent) and never blocks a start.
- **`hooks/tests/test_shell_hooks.py` — 29 tests driving the four repaired shell hooks the way the harness drives them.** Same argument as the existing hook suites: a hook has no importers and produces no diff, and its contract is to fail open, so a dead one is byte-indistinguishable from a healthy one with nothing to say. Each of these is *additionally* silent in its normal case, so "no output" cannot be read as health for any of them. The suite caught a real one while being written — the resolved ruff argv was losing its **last element** to a `printf` with no trailing newline, which formats nothing and reports nothing, exactly the class of silent failure the tests exist for.

- **`pre_pr_check.py` gains a third preflight, `replay` — `rules/merge-hygiene.md` §1, mechanized.** Reports files the default branch still has that this branch **merged in and then lost**: a branch silently reverting somebody else's merged work, which is what a replay built from the wrong base produces (reverse-hunks for files the author never looked at, applied cleanly by `git apply --3way`, landing as ordinary deletion commits). The measured branch dropped **four files another PR had just added** that way — clean apply, mergeable PR, green suite.
  - **The predicate is narrow on purpose, because the obvious version is unusable.** "The base has a file I don't" fires on every branch that is merely *behind*, which is most of them, and a check that fires on correct work gets routed around until none of the gates run. A path is reported only when the base still has it and this tree does not, **and** the commit that added it is already in this branch's history, **and** that commit arrived through a merge rather than through the history the branch was cut from. That last condition is what separates a bad replay from an ordinary cleanup PR deleting a file which predates the fork.
  - **Stated limit:** a branch that **rebases** onto the base rather than merging replays its commits on top of the base tip, so the base's commits land on the first-parent line and read as inherited — deletions after a rebase are therefore treated as deliberate. That is the defensible reading (a rebase genuinely makes those commits part of your line), and the measured failure arrived through merges.
  - Unlike `base` and `scope`, CI *can* in principle see this — the deletions are in the diff. That is why it is missed rather than why it is invisible: a deletion inside your own PR reads as part of your change, and tests catch it only if a test covered the deleted files. In the measured case they did not.
  - Seven tests, all against real temporary git repositories rather than stubbed shas, per the suite's existing rule that the preflights get end-to-end coverage: the failure itself, a merely-behind branch, a pre-fork deletion, the plain green case, all-four-files-reported (a check that names one sends the author back once per file), re-add attribution, and an unresolvable base staying silent. There are deliberately no predicate-only tests — the question is one about *reachability*, and a stub taking two sets of shas would be testing the set subtraction rather than the thing that can be wrong. Every doc site describing the preflight set is updated (`README`, `install-gates`, `rules/merge-hygiene.md`).
- **`rules/merge-hygiene.md` — two rules for the sync itself, both for failures where the tooling *reported success*.** §1 **a clean apply is not evidence of correctness**: re-cutting a stacked branch after its parent squash-merged, a replay patch built from the wrong base **deleted four files another PR had just added**, and `git apply --3way` applied it cleanly and reported success — the only tell was reading the file list. Tools report that they succeeded at what you asked, not that you asked for the right thing. §2 **committed generated artifacts are regenerated, never hand-merged**: derived files conflict on every merge and the correct content is *neither side* — it is whatever the generator produces from the merged tree; two generators in one repo **read the file they rewrite** and die on a conflict marker with an opaque parse error naming only a line number. Includes the count-moved-after-regeneration trap (the artifact may have been stale on the integration branch already) and the durable fix — a `.gitattributes` merge driver, with the honest limit that `.git/config` is not cloned. Sibling to `rules/landing-a-component.md`; referenced from `pr-discipline` §3/§5, `ai-pre-review-checklist`, `verification-before-completion`, `impl-plan-review` Pass 1, and the FLOW.md PRE-PR box.
- **`test-strategy` rule 18 — "passed on retry" is not a diagnosis.** The first time a test passes on retry, run it **N ≥ 5 times in isolation and record the ratio** before moving on; isolation is what separates a nondeterministic test from a suite-interaction effect, and those have different fixes. Measured: one test was re-run once, passed, and was written off as "a flake" — it went on to fail **3 of 5** full-suite runs and turn **two unrelated branches red**, each engineer paying the diagnosis cost from scratch on a failure none of them caused; run three times consecutively in isolation (pass, pass, fail) it was provably nondeterministic, a measurement that took under a minute and was available on day one. Corollary: a bare `assert False` in a flaky test is **doubly** costly — nondeterministic *and* silent when it fires, which is exactly where rule 8 pays most. The existing "flaking 3× / 30 days → quarantined" row is re-framed as the CI-level backstop this rule should keep from firing.
- **`apex-flow` §1a question 0 — measure the primitive before you form a theory.** When something is slow or appears hung, **time the smallest primitive (one connection, one query, one request) before changing any configuration**. Measured: a suite appeared to hang, runs were killed at 180s / 400s / 550s, a hypothesis (disk fsync on a temp directory) was formed and **acted on** — config changed, service restarted — and changed nothing; the primitives, once timed, read **connect 130.06s, create-database 0.27s, migrations 0.19s**. After the fix, **298 tests in 21s against 19m35s for eight tests before**; ~**60–75 minutes** lost between the first theory and the first measurement. Corollary: **"it looks like a hang" is a hypothesis, not an observation** — a kill at 180s observes only that you stopped waiting. Numbered 0 because §1a's existing questions 1–4 all presuppose you know the cost shape; this is how that is earned. Q1's number is unchanged, so `apex:recon`'s "§1a-Q1" reference still resolves.

### Changed

- **`hooks/suggest-skill-on-prompt.sh` routes on announced phase transitions and nothing else — the review-keyword matching is gone, measured 0 for 3.** It demanded a code review on an explicitly read-only audit request, on a message answering four audit questions, and on a status report containing no code, by matching the characters `.py` **inside filenames**. **A grep over prose cannot decide what a message is about** — that is a judgment call, and judgment-dependent work belongs in a skill you invoke. What a grep *can* read is what the author just said they were doing: "let's design this", "ready to plan", "start implementing", "shrink this / support a new kind". Those are announced transitions, each with a freeze that must already have happened, so the three phase-freeze gates (→ `prd-review`, → `design-review`, → `impl-plan-review`) and the subtractive-trap `recon` nudge stay exactly as they were — they were always the cross-prompt backstop to hand-offs the author skills and commands state as mandatory. The `.py` / `.tsx` / API-surface blocks are deleted; the review skills themselves are untouched. Also switches the emit to `jq -Rs`, matching `apex-primer.sh` and `suggest-skill-on-edit.sh` — the raw `printf` it used could produce invalid JSON that the harness drops **silently, with a zero exit**, which is a gate that stops firing and never says so. The three measured messages are now regression fixtures, each verified to fire the old matcher and not this one. **Precision discipline for anything added here: match a stated intention, never a topic.**
- **`hooks/run-python-hook.sh` defers to the host repo's own copy of a hook, per script.** A repo that keeps `.claude/hooks/session_collisions.py` registers it itself, and apex registering its fork of the same filename means **both run** — the measured session received two collision reports at one startup, one carrying the repo's current claims data and one from apex's staler fork. The failure is not an error, it is a *second answer*, with nothing to say which is current. Guarding in the shim rather than in the two duplicated scripts fixes both at once and is the correct portable behaviour for a plugin meant to work anywhere: **ship the hook for repos that lack it, defer to repos that have their own.** Checked per script, so a repo that forked one still gets the other two. Drains stdin before deferring, so the harness's write cannot land on a closed pipe.
- **`hooks/format-on-save.sh` runs the repo's *pinned* ruff instead of whatever is on `PATH`.** The defect was disagreement, not absence: the edit-time formatter resolved a floating install while every gate ran the pin — twelve patch versions apart in the measured case — so the formatter could produce output the commit gate then rejected, and the remedy the gate printed was undone by the next keystroke. Precedence follows what a repo has actually declared: an explicit `RUFF_VERSION = "ruff==X.Y.Z"` in `ci/pre_pr_check.py` (**read**, not restated — `ci/hooks/pre-commit` already reads it, and restating it makes a third version to drift), else the `uv run` / `poetry run` lockfile rule `templates/gates/pre_pr_check.py`'s own `_runner()` uses, else `PATH`. A repo whose pin lives behind `uv` also loses the second defect — the old line did nothing at all, silently, when ruff was not installed. An unformatted file that reaches the default branch reddens *every open PR*, because PR CI builds a merge ref.
- **`hooks/suggest-review-on-stop.sh` counts this session's edits, not the worktree's.** It measured "your uncommitted code edits" as `git diff HEAD` plus untracked files at the repo root; in a worktree shared by concurrent sessions that is *everyone's* edits, and it charged one session **573 lines it had not written**. It now subtracts `session-baseline.sh`'s SessionStart snapshot before counting. A file that was already dirty and is edited again still counts (its hash moved), and its whole diff vs HEAD is then attributed here — that over-states one file but never invents one. **An absent baseline fails open toward nudging** — a snapshot that could not be taken should cost precision, never silence the review. Restores a signal that currently has to be dismissed on sight.

- **`pr-discipline` §1 gains the mechanical reason for draft-default, which is stronger than the cultural one.** **A conflicting PR gets no CI at all** — the forge cannot build a merge ref, so no workflow is dispatched, and the CLI's **"no checks reported"** is byte-identical to a queue that has not started. Measured: a branch holding six issues for eleven hours was, at the moment its PR opened, **both behind by 23 commits and conflicted** — it had **never once been built**, and nothing in the tooling said so. Hence: **open the PR on commit one, as a draft** — the draft is not a publication, it is the instrument that tells you a merge ref can be built. Adds the three-state check-reading rule (`mergeable: CONFLICTING` is red, not pending).
- **`pr-discipline` §2 gains an explicit carve-out so §1 and §2 no longer appear to contradict.** "Push once" prices reviewer noise and CI spam on a *published* PR; a draft has no audience, so an extra push there costs ~0 and buys the mergeability signal §1 needs. **Push freely to a draft; squash before marking ready-for-review** — the squash discipline attaches to the *ready* transition, not the first push.
- **`pr-discipline` §2 gains "don't duplicate CI locally".** Run the narrowed scope your change can reach; push, and let CI prove the rest. Measured: a ~6,300-test suite run locally **six times in one session at ~4 minutes each** — ~**25 minutes of pure waiting**, mostly re-proving what CI proves on push. The four cheap pre-commit gates (build / lint / format / types) are unchanged; only the test step is scoped.
- **`templates/gates/pre_pr_check.py` — the `TEST_SELECTOR` fallback is qualified.** "Absent or failing, the full suite runs" is safe only where reachability is *genuinely unknown*. A selector that answers "run everything" for a path it does not *recognize* charges every developer four minutes for its own missing mapping — a frontend file cannot reach a backend package. Where reachability is provable, encode it; those are the mappings worth writing first. (Also picks up a pre-existing `ruff format` violation in `preflight`, which was failing `--check` at HEAD.)
- **`pr-discipline` §3 gains rules 7 and 8** — cap branch *lifetime*, not only size (pointer to `impl-plan-review` Pass 1); and verify the changed-file set after any replay (pointer to `rules/merge-hygiene.md` §1). The `git rebase --onto` how-to now says what to do next: getting `<old-base>` wrong is silent, because the replay still applies cleanly and what it drops is somebody else's merged work.
- **`impl-plan-review` Pass 1 — size has two dimensions, LOC *and* lifetime.** A PR under 400 LOC that stays open for a day against a moving base is not a small PR, and the plan is where the second factor is decided. Measured: one branch carried **six issues for eleven hours**; the integration branch moved **23 commits**, forcing **three separate merges** — each a conflict resolution plus artifact regeneration plus re-verification — and the stacked child then needed a **full re-cut** after the parent squash-merged. New pass condition: each PR states an expected open-to-merge lifetime budgeted **in hours**, and carries **one issue**; budget one forced merge per ~8 commits of base movement. New adversarial counter-pass: count what the base will do underneath the longest-lived layer, and name the child that will need a re-cut — unbudgeted work in every plan that does not name it.
- **`rules/landing-a-component.md` §1** — the existing "a branch that must live for days has one ending" clause gains the measurement above, and its applied-in row now names `impl-plan-review` Pass 1 and `merge-hygiene.md`.
- **`verification-before-completion`** — two new rows (merge/rebase/cherry-pick/patch → read the changed-file set; conflict in a generated artifact → regenerate in dependency order, byte-stable on a second run), and two new entries under *What does NOT count as verification*: **"the tool said it succeeded"** and **"it hung."**
- **`ai-pre-review-checklist`** — Definition of Ready leads with the changed-file-set check, flagged as **the one item a reviewer cannot check for you**: a replay from the wrong base applies cleanly, reports mergeable, and passes every test, because the work it deleted is not in your diff's story.
- **`FLOW.md`** — merge-hygiene added to the PRE-PR box; the draft-on-commit-one mechanic added to the OPEN PR box.
- **Test-rule count 17 → 18** across all 11 sites in 9 files (`README`, `FLOW.md`, `commands/test.md`, `test-strategy` ×3, `test-coverage-audit`, `python-review` ×2, `typescript-review` ×2), per `MAINTAINING.md` §2. The `17 rules` / `17 language-agnostic` greps miss `test-strategy`'s own "the 17 methodology rules" phrasing — a third pattern worth adding if that grep is ever mechanized.

## [0.4.0] — 2026-08-02

### Added

- **`templates/` — the blank forms apex's gates review.** apex has always told you to write a PRD, a design and an impl-plan, and shipped no form for any of them: every author invented the shape, so no two artifacts were comparable and review re-derived what "done" meant each time. Five skeletons (`recon`, `prd`, `design`, `impl-plan`, `adr`) written to the existing `docs/<feature-slug>/` convention, plus `templates/github/` (a PR template and two issue forms) for `apex:install-gates` to install. Wired into the steps that author each artifact — `apex:recon`, `apex:design-feature`, `apex:architecture-design`, `apex:adr-review`, `/apex:prd`, `/apex:impl-plan`. Resolution is **repo first, plugin second**: a repo with its own `docs/templates/<name>.md` keeps it, every other repo gets apex's the moment the plugin is installed, and the injected message names which one it used. The GitHub issue form keeps two hard-won fields — a **Kind** option reading *"Wiring / adoption — something built but consumed by nothing"*, and a **required "Production caller"**, because the most-repeated defect it exists to catch is a capability that passes every gate and is consumed by nothing.
- **`artifact_templates.py` hook (PreToolUse on Write and on Bash) — the check that the artifact was actually written.** On `Write`, injects the matching form when a session creates a PRD / design / impl-plan / recon / ADR. On `Bash`, checks `gh pr create` / `gh issue create` bodies against the repo's `.github/` templates and **names the sections the body is missing**. GitHub applies those templates only in its web UI — `gh pr create --body-file …` skips them entirely, which is how an agent files nearly every PR and issue, so for the actor filing most of a repo's artifacts they were decorative. Issue forms are discovered and routed at run time from the `--template` / `--label` / title-prefix signals each form declares about itself, so a new form is routed the moment it is added. Adding an artifact type is one row in `DOC_RULES` plus a file in `templates/`.
- **`session_collisions.py` hook — apex's first `SessionStart` hook, and the one fact a session cannot learn for itself.** Names the other Claude Code sessions active in this repo right now (title, branch, worktree) and flags a **COLLISION** when one shares your branch, your worktree, or the work item your branch names. Measured cost of not having it: eight concurrent sessions in one repo, two of which independently claimed the same work item and cut two branches for it — one held the finished, fully-tested component, the other held nothing. The non-obvious part is preserved in the hook's own docstring: the harness keys `~/.claude/projects/<slug>` on the directory `claude` was **launched from**, not on the repository, so a session started in a worktree gets its own project directory and a single-directory scan finds only itself — silence indistinguishable from "no collisions". It resolves the main checkout via git's `commondir` and scans every project directory sharing that prefix. Liveness is inferred from transcript mtime and is stated as the heuristic it is ("active recently", never "running now").
- **`install-gates` skill + `templates/gates/` — the blocking half of the enforcement split.** A Claude Code plugin can ship skills, hooks, commands, rules and templates; **it cannot ship CI**. So apex's enforcement is three tiers with three different populations — hooks bind Claude Code sessions only (advisory, fail-open), a local pre-PR script binds only whoever runs it, and a CI job binds everyone and blocks the merge — and only the last one apex cannot hand you finished. The README now states that split up front, because a user who installs the plugin and assumes they have blocking gates finds out at the worst possible moment. `install-gates` scaffolds the third tier into a target repo: detect the CI host, copy the two gates in, wire the `pull_request` job, declare the repo's custody paths, then make the check required. Ships two vendored gates:
  - **`pr_body_check.py`** — requirements **derived from the diff**, never fixed: any PR needs *What this does* + *Why this shape*; one that changes shipped source also needs *Test plan* + *Wiring*; one that **adds** shipped source also needs a *Reuse verdict*; one touching a custody or trust path also needs a *Risk note*. A gate demanding every section of every PR fails on a typo fix, and a gate that fires on correct work teaches people to reach for `--admin`, which skips every other check at once. A heading alone does not count — content identical to the template's placeholder is treated as absent. The escape hatch (`<!-- pr-body-check: skip — <why> -->`) requires a real reason and is echoed to the job log; a bare marker is rejected. Sensitive paths are read from a `[tool.apex]` block (`pyproject.toml` or `.apex.toml`) rather than shipped as a guess — unconfigured, the Risk-note requirement simply never fires.
  - **`pre_pr_check.py`** — runs what CI runs, for this branch's diff, cheapest gate first, **reusing the CI jobs' own commands** so "pre-PR passed" and "CI passed" cannot drift into two definitions of green. Its two git preflights cost milliseconds and CI *cannot* replicate them: **base** — a commit whose subject ends in `(#123)` was written by the forge's squash merge, so one sitting in `origin/<default>..HEAD` means the branch was cut from a base the default branch has since rewritten (invisible precisely because nothing is broken — the merge is legitimate, the forge reports it mergeable, the tests pass; it just lands two editions of someone else's change); **scope** — a branch whose every commit declares `docs(...)` has no business carrying source files.
- **`rules/landing-a-component.md` — three rules that cost a day when broken.** A slice that does not touch the target package is not a slice of that component (twelve slices, the five that closed all landed in *other* packages; merging them moved a dependency underneath the long-lived branch holding the real work, and one conflicted test file then blocked 9,085 green, fully-tested lines for a day). A design may be at most one revision ahead of code — the corollary of `apex-flow` §12, referenced rather than restated. Branch name matches worktree name, and one slice means one branch.
- **`.github/workflows/hook-tests.yml`** — paths-scoped CI for the Python hooks (63 tests). A hook is uniquely easy to break silently: no importers, no diff, and fail-open by construction, so a dead hook emits nothing and exits 0 — exactly like a healthy one with nothing to say. A dropped `import json` did precisely that once. `session_collisions.py` has the sharper version of the same edge, since silence is its *normal* output.

- **The SHIP phase (FLOW.md phase 8) — apex's pipeline no longer ends at "merged".** Three new skills close the post-merge hole the full-lifecycle review found (`docs/research/full-lifecycle-roadmap.md`):

  - **`cicd-review` skill** — pipeline-as-code gate treating a CI workflow as a **privileged program that runs other people's input**: least-privilege `permissions:`, the `pull_request_target` trap, untrusted-interpolation injection, **SHA-pinned third-party actions**, cache poisoning, `test-strategy` CI-tier mapping, timeouts + concurrency, **OIDC federation over stored cloud keys**, lockfile determinism, idempotent re-runs.
